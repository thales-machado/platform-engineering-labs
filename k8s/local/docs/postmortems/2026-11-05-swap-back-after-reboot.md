# 2026-11-05: Swap came back on urahara after reboot, kubelet down

- Status: resolved
- Severity: medium (control plane down after reboot; lab cluster only)
- Found during: reboot drill after step 1.12

## Summary

In step 1.3, swap on urahara was turned off and its line in `/etc/fstab` was commented out. After the first planned reboot, swap was on again and kubelet refused to start (`running with swap on is not supported`), so the API server never came up. systemd's GPT auto-generator had activated the swap partition by its partition type, without fstab. Turning the generator off in the kernel command line (`systemd.gpt_auto=0`) fixed it, and a second reboot confirmed it.

## Impact

- The only control plane was down for about 10 minutes after the reboot (API server not running).
- Running pods on zangetsu kept running; the cluster could not be managed and no changes could be scheduled.

## Root cause

On Debian 13 (systemd 257), `systemd-gpt-auto-generator` activates swap partitions on the root disk that have the GPT "Linux swap" partition type, even when they are not in `/etc/fstab`. Commenting out the fstab line in step 1.3 only removed one of the two ways the partition was activated. `swapoff -a` hid the problem until the next boot.

## What fixed it

- Kernel parameter `systemd.gpt_auto=0` in `GRUB_CMDLINE_LINUX_DEFAULT`, then `update-grub`. Debian mounts `/` and `/boot/efi` from fstab, so nothing else depends on the generator.
- The mask on `dev-nvme0n1p3.swap` was kept; it is harmless.

## Lessons

- A change made at runtime (`swapoff -a`) is not a change that survives a boot. Test persistence with a reboot, not with a status command.
- There can be more than one source for the same setting (fstab and a systemd generator). Check what systemd actually loaded: `systemctl list-units --type=swap --all`.
- Masking a unit by an alias is not reliable when the real unit name is generated.
- The reboot drill was planned as an action of the previous postmortem and found this on its first run.
